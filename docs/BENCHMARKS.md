# Benchmark protocol

Performance claims are valid only when a report records all of the following:

- Pandoracle, Python, PyArrow, SQLite, DuckDB, kernel, and distribution versions.
- CPU model/core count, RAM, storage model/transport, filesystem, mount options,
  and whether LUKS is active.
- Synthetic generator seed, row count, RAW size, value distributions, duplicate
  rate, and indexed semantic fields.
- Cold versus warm cache state and the method used to establish it.
- Import phase times, bytes read/written, rows per second, peak RSS, temporary
  space, final RAW/Parquet/index sizes, and failure count.
- Query p50/p95/p99, candidate/result count, and dataset segment fan-out.

The reference machine class is 4 CPU cores and 16 GB RAM with an external USB
3.x SSD and ext4. Results from an internal NVMe drive must be labeled separately.

Do not place arbitrary generated values in sequential order if production-like
queries will have skew and duplicates. Always include high-cardinality keys,
frequent duplicates, absent values, and negative lookups. Publish the generator
and seed with the result.

The 32 GB target describes total workspace capacity, not RAW corpus size. RAW,
Parquet, index, staging, and at least 20% operational reserve must all fit.

Run the developer full-path warm benchmark with:

```console
python scripts/benchmark_exact.py /path/to/workspace \
  person42@example.test \
  --type email \
  --warmup 10 \
  --iterations 1000 > benchmark-results/exact-email.json
```

The report deliberately omits the query value. This command does not drop Linux
page cache and therefore must not be labeled a cold-cache benchmark.

The 0.3 three-layer implementation has a small synthetic policy smoke report at
[`benchmarks/profile-policy-smoke-2026-09-02.md`](benchmarks/profile-policy-smoke-2026-09-02.md).
It is explicitly not the 1 GB acceptance result.

The 1 GB development-VM comparison against GNU grep, ripgrep, GNU Awk, and
DuckDB is at
[`benchmarks/architecture-comparison-1gb-vm-2026-09-12.md`](benchmarks/architecture-comparison-1gb-vm-2026-09-12.md).
It uses a qualifying RAW byte count, but remains a diagnostic rather than the

The import-throughput regression diagnosis, including 20 batch intervals,
stage attribution, CPU/I/O evidence, and the aborted-import cleanup finding, is
at [`benchmarks/import-throughput-profile-2026-09-02.md`](benchmarks/import-throughput-profile-2026-09-02.md).
It is also a diagnostic synthetic run, not the 1 GB acceptance result.

## M2 durability acceptance campaign

M2 uses one campaign rather than a new runtime benchmark subsystem. Run it on
the reference machine above with deterministic synthetic CSV and record a 1 GB
RAW checkpoint plus a full 10 GB RAW result. Calibrate row counts first and
record exact generated byte sizes; the acceptance thresholds are at least
1,000,000,000 and 10,000,000,000 source bytes, not estimated row counts.

For both checkpoints record uninterrupted import phase times, throughput, peak
RSS, temporary high-water space, final RAW/record/canonical/acceleration sizes,
full `verify`, and search latency. At 10 GB also exercise these representative
durability failures with the test-only fault mechanism or an equivalent process
signal:

1. hard exit after RAW rename but before its catalog row;
2. Ctrl-C during streaming transformation with populated staging;
3. hard exit after the final artifact renames but before catalog publication;
4. hard exit during GC after candidates move to trash and after its catalog
   commit.

For every interruption record catalog status and active pointers before
recovery, `recover` output, GC dry-run JSON, GC apply JSON, the second empty GC
plan, retry result, and final verification. Confirm that the previous published
generation remains readable throughout, exactly one new generation is published
after retry, and FAILED/ABORTED operation tombstones remain.

The report must include commands, fault points/signals, generator seed and data
shape, software/hardware/storage/filesystem details, wall time, and peak RSS.
Runs on the current development VM or internal system disk may be useful
diagnostics but cannot close this acceptance item.

## Universal-search matrix

Run the same deterministic query manifest at both checkpoints. The manifest
must contain present, absent, frequent, and rare values without persisting real
query data. Use these workload classes:

| Workload | Required profile and query shape | Evidence |
| --- | --- | --- |
| High-cardinality VALUE | VALUE on an identifier; present and absent EXACT | cold/warm p50/p95/p99, postings and bytes |
| Skewed TOKEN | TOKEN on PERSON_NAME; one frequent, one rare, and two-token clues | candidate cardinalities, peak RSS, latency |
| Range | VALUE on DATE/DOB; single year and multi-year inclusive ranges | returned count, latency, access path |
| Mixed | VALUE seed plus TOKEN and range filters | every explain step and row reduction |
| Fan-out | the same semantic clue across at least four active datasets | deterministic order, aggregate estimate, wall time |
| Scan-only | disable acceleration, then repeat EXACT, TOKEN, range, and fan-out | predicted/actual time and permission behavior |

For each profile, save `acceleration plan` JSON before the build and
`acceleration show --history --format json` after it. Record estimated size and
time, actual artifact bytes and build wall time, prediction error, and build
throughput. Build VALUE and TOKEN separately as well as together so primitive
coefficients are attributable. Confirm that disable does not read or rewrite
canonical Parquet and that rebuild preserves DatasetVersion and RecordRefs.

For search, save `search --explain --format json` output and an external timing
record. The explain document supplies access paths, projected bytes, operator
evaluations, predicted duration, actual scan duration, and materialization
duration. Run warm trials in one unchanged profile and process environment.
Establish cold trials by a documented reboot or cache-eviction method on the
reference host; never label a new process with an uncontrolled OS cache as
cold. Capture peak RSS externally for every workload.

Compare high-cardinality VALUE p95 with the archived pre-v2 exact-search
baseline on the same corpus, query manifest, machine, storage, cache method,
warmup, and iteration count. Acceptance requires no VALUE p95 regression. Also
verify deterministic results with clue order reversed, `--scan` on accelerated
queries (it must not force SCAN), and a scan estimate above the permission
policy both without and with `--scan`.

The final report has separate 1 GB and 10 GB tables for latency, prediction
error, peak RSS, interruption/recovery, and storage overhead. It includes raw
JSON artifacts or checksums for them, exact commands, software versions, CPU,
RAM, storage, filesystem/mount details, generator seed, row count, and exact
source bytes. This protocol is complete, but its acceptance boxes remain open
until it is executed on the reference machine class.
